# Протокол CyberCord

CyberCord — сеть без серверов. Каждый запущенный клиент является полноценной нодой:
он хранит свои чаты, помогает другим соединяться (relay), раздаёт файлы и участвует
в DHT. Этот документ описывает, как устроена сеть в версии 0.10.

![Как ноды находят друг друга](img/guide-1-network.svg)

## 1. Транспорт и идентичность

| Слой | Что используется |
|---|---|
| Идентичность | ключ Ed25519, ID = libp2p PeerId (`12D3Koo…`), файл `identity.key` в папке данных |
| Транспорт | QUIC (UDP) и TCP, порт по умолчанию **47100**, при занятом порте — случайный |
| Шифрование соединения | Noise (TCP) / TLS 1.3 (QUIC) |
| Мультиплексирование | yamux |
| Рассылка | gossipsub (подписанные сообщения, `ValidationMode::Strict`, до 1 МБ) |
| Поиск нод и имён | Kademlia, протокол `/cybercord/kad/1.0.0`, режим сервера |
| Файлы (как торрент) | request-response, протокол `/cybercord/files/1`, CBOR |
| За NAT | Circuit Relay v2 (каждая нода — relay, лимит 30 мин / 64 МБ на цепь), DCUtR (hole punching), UPnP |
| Локальная сеть | mDNS |

Дедупликация gossipsub — по хэшу содержимого сообщения. Поэтому все сообщения,
которые могут повторяться (запросы истории, запросы файлов, ответы с историей),
несут случайный `nonce` — иначе повтор отбрасывался бы как дубликат.

## 2. Как нода находит других (без сканирования)

CyberCord **не перебирает IP-адреса в интернете**. Подключение идёт только к
адресам, которые ноды сами о себе объявили:

1. **mDNS** — ноды в одной Wi-Fi/LAN.
2. **Сохранённые ноды** — `peers.json`, до 500 записей, при старте дозвон по свежести.
3. **Друзья** — адреса из кода подключения (`/ip4/…/p2p/<ID>`) или поиск по ID в DHT.
4. **Обмен списками (PEX)** — каждые 15 с нода публикует в `cc/control` себя и до 24
   самых свежих известных нод.
5. **Kademlia DHT** — `get_closest_peers` для поиска по ID, bootstrap раз в минуту.
6. **Глобальная точка встречи — Mainline DHT (BitTorrent).**
   Ключ: первые 20 байт `BLAKE3("cybercord/rendezvous/v1")`.
   * Нода, до которой можно достучаться (публичный IP или UPnP), делает
     `announce_peer(key, quic_port)`.
   * Все ноды делают `get_peers(key)` и дозваниваются до найденных
     (`/ip4/<ip>/udp/<port>/quic-v1`), не больше 16 за раунд, один адрес — не чаще раза в час.
   * Если никого нет — повтор через 10 с, 20 с, 40 с … до 5 мин; если нашли — раз в 15 мин.
   * Отключается в Настройки → Приватность (`"global": false`).
7. **Relay + hole punching** — ноды за NAT получают резервацию у доступной ноды
   другого пользователя, затем DCUtR пробует прямое соединение.

Цель — 8 соединений; дозвон до 5 новых нод за раунд.

## 2а. Короткие ники (0.21)

`@<имя>-<хвост>`: имя — транслитерация отображаемого имени (a–z, 0–9, `_`,
до 16 знаков), хвост — 6 знаков Crockford base32 из первых 30 бит
`blake3("cybercord/handle/v1/<PeerID>")`. Узел объявляет себя провайдером
ключа `blake3("cybercord/handle-key/v1/<хвост>")` в Kademlia. Ищущий берёт
провайдеров этого ключа и оставляет только тех, чей PeerID даёт тот же
хвост, — так ник нельзя подделать. Имя в нике — только для людей.

## 2б. Сквозное шифрование и письма (0.22)

* `Wire::Keys(KeyBundle {peer, x25519, mlkem, ts_ms, sig})` — открытые ключи
  шифрования, подписанные Ed25519-ключом личности (тема control, повторяется
  с профилем). Принимается только с верной подписью того же `peer`.
* `Wire::Sealed {from, to, id, epk, kem, nonce, ct}` — личное сообщение:
  эфемерный X25519 → секрет 1; ML-KEM-768 encapsulate → секрет 2;
  ключ = HKDF-SHA256(секрет1‖секрет2, salt `cybercord-hybrid-x25519-mlkem768`,
  info = ID обоих, epk, kem); XChaCha20-Poly1305, случайный nonce 24 байта.
  Внутри — подписанный `ChatEvent`; его `from` обязан совпасть с `Sealed.from`.
  Открытый текст выравнивается до кратного 256 байтам.
* Письма: отправитель, если друг не подключён, публикует
  `MailPut {item: Sealed}` в `cc/mail/<хранитель>` (до 3 хранителей с флагом
  `keeper` в пульсе, по убыванию score). Хранитель объявляет провайдера
  `blake3("cybercord/mailbox/v1/<получатель>")`. Получатель ищет провайдеров
  своего ключа, подключается; хранитель шлёт `MailDrop {items}` в
  `cc/mail/<получатель>`, тот отвечает `MailAck {ids}`, хранитель удаляет.

## 3. Темы gossipsub

| Тема | Назначение |
|---|---|
| `cc/control` | пульс нод (`Score`), обмен списками (`Peers`) |
| `cc/ch/<сервер>/<канал>` | текстовый канал |
| `cc/ch/city.<направление>/<канал>` | канал направления карты-города (0.18): `chat`, `projects`, `help`; голос — `city.<направление>/room` |
| `cc/dm/<ID_a>/<ID_b>` | личка (ID упорядочены, тема одинакова у обоих) |
| `cc/voice/<сервер>/<комната>` | голосовой канал |
| `cc/voice/cc/dm/…` | личный звонок |

## 4. Сообщения (`Wire`, JSON)

| Тип | Поля | Зачем |
|---|---|---|
| `Chat` | `ChatEvent {id, channel, name, body, ts_ms, attach?, from, sig, edits?, rev, deleted}` | сообщение, правка или удаление (с 0.12 подписано автором) |
| `History` | `ev, nonce` | ответ на запрос истории |
| `SyncReq` | `channel, since_ms, nonce` | «пришлите, что было после…» (ответ — до 50 сообщений) |
| `Score` | `peer, name, score, ts_ms, reachable, voice?, listed, status` | пульс раз в 5 с: выбор хаба, присутствие, кто в каком голосовом канале, каталог имён |
| `Peers` | список `PeerRec {peer, addrs, last_seen_ms}` | обмен списками нод |
| `Profile` | `peer, name, avatar?, interests, activity, skills [{id, level, note}], job, tasks, rev, ts_ms, sig` | профиль, подписанный владельцем (тема управления; при изменении, при новых соединениях и раз в 2 минуты) |
| `Voice` | `room, name, seq, pcm` | 20 мс голоса, 48 кГц моно i16 |
| `BlobChunk` | `hash, idx, total, round, data(base64)` | кусок файла (192 КБ) |
| `BlobReq` | `hash, nonce` | «у кого есть этот медиафайл?» (GIF, картинки, кружки, музыка ≤ 16 МБ) |
| `FileWant` | `hash, nonce` | «у кого есть этот файл?» — владельцы сами подключаются к спросившему |

## 5. История чатов

* Каждое сообщение сохраняется у каждого получателя (`channels/<сервер>__<канал>.jsonl`).
* При открытии канала и при появлении нового участника комнаты нода отправляет
  `SyncReq` с временем последнего известного сообщения; участники отвечают `History`.
* Отдельно каждые 5 с проверяется, с кем в открытых комнатах ещё не синхронизировались.

## 5а. Правка и удаление сообщений (0.12)

* С 0.12 в каждом `ChatEvent` есть `from` (ID автора) и `sig` — подпись Ed25519
  ключом автора над `id, from, ts_ms, name, edits, rev, deleted, вложение, body`
  (канал не входит: личка у двух сторон хранится под разными именами).
  Так автор доказуем и тогда, когда сообщение пересылает кто-то другой при
  синхронизации истории. Сообщение с неверной подписью отбрасывается.
* **Правка** — новое событие с `edits = <id сообщения>`, новым `body` и
  `rev` = номер версии (2 — первая правка). **Удаление** — то же с `deleted = true`.
* Правка и удаление учитываются, только если подписаны **тем же** ID, что и
  исходное сообщение. Старые сообщения без подписи (до 0.12) показываются, но
  изменить их нельзя.
* Правки ходят и синхронизируются как обычные сообщения, поэтому опоздавший
  участник получает уже исправленный текст.
* В чате у исправленного сообщения стоят индекс и дата, как в общей семантике:
  «ред.₂ · 21.11 18:10»; при наведении видны все версии (в₁, в₂ …) с датами.
* При удалении нода стирает у себя текст и вложение исходного сообщения и его
  старых версий; само событие удаления остаётся, чтобы дойти до тех, у кого
  сообщение ещё есть. Гарантировать удаление у чужих нод (например, у старых
  версий CyberCord) нельзя — это честное ограничение сети без сервера.

## 6. Файлы, GIF, кружки, музыка, голосовые

* Файл адресуется по `BLAKE3` от содержимого, лимит 16 МБ.
* Отправитель публикует куски в тему канала; получатель собирает, проверяет хэш, сохраняет в `blobs/`.
* Чего не хватает — запрашивается `BlobReq` до 6 раз; отвечает любой, у кого файл есть
  (не чаще раза в 4 с на файл и раза в 15 с одной и той же ноде).
* Поэтому файл доступен, даже когда автор офлайн.

| Вид | Формат |
|---|---|
| GIF / картинка | как есть (GIF, PNG, JPEG) |
| Видео-кружок | JSON: кадры JPEG 240×240 @15 к/с + PCM-звук |
| Музыка | mp3 / flac / ogg (Vorbis) / wav / m4a (AAC), декодируется symphonia |
| Голосовое | WAV 16 кГц моно, имя `voice-message.wav`, до 5 мин |

## 6а. Файлы любого размера (как торрент)

* Файл до 8 ГБ режется на куски по **256 КБ**. **Манифест** — размер и BLAKE3
  каждого куска; ID файла — BLAKE3 всего файла. В чат уходит только сообщение с
  `Attachment {kind: File, hash, name, size}`; сам файл никому не рассылается.
* Скачивание — по нажатию «Скачать» (очередь сохраняется в `downloads.json`):
  1. **кто может отдать:** участники комнаты, где файл отправлен (подписчики
     темы), плюс провайдеры в Kademlia по ключу
     `BLAKE3("cybercord/file/v1/" + hash)`;
  2. если данные не идут — каждые 15 с в комнату публикуется `FileWant`, и ноды,
     у которых есть хоть часть файла, **сами подключаются** к спросившему; DHT
     опрашивается каждые 20 с;
  3. запрос `Manifest`, затем `Piece{idx}` — до 32 кусков одновременно, до 8 с
     одной ноды, порядок случайный, чтобы разные ноды отдавали разные куски;
  4. каждый кусок проверяется по манифесту и пишется прямо в `<имя>.part`;
     карта готовых кусков сохраняется каждые 2 с;
  5. когда всё скачано — проверка BLAKE3 всего файла в фоне. Если совпало —
     файл переименовывается и нода начинает его раздавать
     (`start_providing`). Если нет — манифест берётся заново у другой ноды.
* Раздают все, у кого есть куски: автор (с исходного места на диске), те, кто
  скачал, и те, кто качает сейчас (уже готовые куски).
* Имена файлов очищаются (`../`, `\`, служебные символы), файл не может
  оказаться вне папки загрузок.

## 6б. Статусы и фоновая работа

* Статус (`"", online, offline, work, sleep, busy, learning, relax, play, read`)
  идёт в поле `status` пульса. `offline` — невидимка: нода работает и помогает
  сети, но для других вы не в сети.
* «Искать новых пользователей» выключено → нода не дозванивается до незнакомых
  нод из обмена списками, LAN и глобальной DHT, но держит известные ноды и друзей.
* При закрытии окна процесс продолжает работать в трее (StatusNotifierItem через
  D-Bus на Linux, область уведомлений на Windows).

## 7. Голос

* Захват с выбранного устройства → громкость ввода → шумовой порог
  (авто: следует за фоном, ×3.5, −48…−24 дБ; вручную: −100…0 дБ, удержание 300 мс)
  → ресемплинг в 48 кГц → кадры по 20 мс.
* Приём: очередь до 2 с → ресемплинг в частоту устройства → громкость вывода.
* Кто в какой комнате, видно из поля `voice` в пульсе (личные звонки не объявляются).
* **Звонки (0.20):** `Wire::Call {id, kind, name, round}` по личной теме
  `cc/dm/<a>/<b>`; принимается только от того друга, чья это тема.
  `kind`: `ring` (повторяется каждые 3 с, `round` растёт, чтобы gossip не
  отбрасывал повтор), `accept`, `decline`, `cancel` (звонящий передумал),
  `end` (повесили трубку), `busy`. Звук — как раньше, по
  `cc/voice/cc/dm/<a>/<b>`. Старые версии неизвестный тип просто пропускают.
* `VoiceFrame.bot` (0.19, по умолчанию `false`, в JSON только когда `true`):
  кадр от тестового бота режима разработчика; эхо-бот такие кадры не
  повторяет. Старые версии поле просто игнорируют.

## 8. Хаб (виртуальный центральный узел)

Сервера нет, но для координации выбирается «хаб» — самая подходящая нода из живых:

```
score = 0.35·доступен_из_интернета + 0.30·min(аптайм/30 мин, 1)
      + 0.25·min(соединения/8, 1) + 0.10·стабильная_случайность(ID)
```

Хаб и резерв видны всем одинаково (детерминированный выбор по пульсу).

## 9. Поиск людей и карта сети

* **Каталог** — имена из пульса (`listed = true`), сохраняются в `directory.json`
  (до 5000 записей), поэтому находятся и офлайн-пользователи.
* **Индекс имён в Kademlia** — нода с `listed = true` объявляет себя провайдером ключей
  `BLAKE3("cybercord/name/v1/" + префикс)` для каждого префикса имени длиной 3…24
  и для каждого слова имени. Поиск = подстрока по каталогу + `get_providers(префикс)`;
  найденные через DHT ноды получают дозвон (до 8), и их пульс приносит имя.
* **Карта** — снимок адресной книги раз в 1,5 с: соединён ли, тип соединения
  (`lan`/`direct`/`relay`), откуда узнали (`lan`, `saved`, `friend`, `node`, `global`,
  `exchange`, `dht`, `search`, `identify`), relay в какую сторону, в сети ли.

## 10. Безопасность — честно

* Соединения шифруются (Noise/TLS). Relay пересылает только зашифрованные байты.
* **Сообщения в личках не шифруются сквозным ключом друзей.** Нода, знающая оба ID,
  может подписаться на тему лички. Сквозное шифрование (MLS) — следующий шаг.
* Сообщения gossipsub подписаны ключом автора, а с 0.12 подпись есть и внутри
  самого сообщения: подделать чужое сообщение, правку или удаление нельзя,
  даже при пересылке истории третьими нодами.
* Включённый глобальный поиск раскрывает участникам DHT BitTorrent, что ваш IP
  пользуется CyberCord.
